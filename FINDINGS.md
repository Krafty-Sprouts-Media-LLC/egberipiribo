# FINDINGS

Every place the theme handbook was missing, wrong or unclear, and every missing theme feature or socket (a **wall**).
Each has what I expected and what I did instead. Marks: **doc** = the handbook or reference is wrong or silent;
**wall** = a feature or socket Teme does not have yet for a theme.

## From the lead (foundation, build, layout)

| # | Kind | Finding | Expected | Did instead |
|---|---|---|---|---|
| 1 | doc + wall | `docs/reference/theme-manifest.md` says `tokens` is "Design token, then its CSS value" and `tokens.base`/`accent` are hex colours, so any token name looks allowed. Activation and `teme:theme:check` refuse any token not in a fixed list (base, contrast, accent, on-accent, muted, rule, font-body, font-heading, font-mono, step--1..step-5, space-1..space-8): "Unknown token "body"…". The list appears only in the error message. | Free token names (`surface`, `font-display`, `radius`), written as `--teme-*`. | Kept the allowed tokens in the manifest; derived the rest in the skin CSS with `color-mix()` from `--teme-contrast`/`--teme-base`. Wall for skins: a later skin cannot ship its own named tokens, nor a second brand colour (the pattern sample 2's `--color-accent`). |
| 2 | doc | The handbook has no page on building a theme's assets: how a theme's own Vite build is set up (entries, `base`, `publicDirectory`, committed `public/build`), that `fonts` and the build's `url()` paths are relative to the theme's `public` folder, or that core serves the theme at `/themes/{code}/`. I learned it from the default theme's README and its `vite.theme.config.ts` in Teme's own repository, which an outside developer would not have. | A "Theme assets" page: `package.json`, `vite.config`, `assets.manifest`, where fonts go, the `teme.theme` layer name. | Copied the default theme's pattern: `base: '/themes/{code}/build/'`, `publicDirectory: 'public'`, `buildDirectory: 'build'`, `hotFile: 'public/hot'`; the cascade layer `teme.theme` taken from the default theme's stylesheet header. |
| 3 | doc | `php artisan teme:themes:link` (links each theme's `public` into `public/themes`) is needed on a development site before a theme's built CSS and fonts load, and is not in `start/development-site.md` or `first-theme.md` (only in the default theme's README). | A step "run `teme:themes:link`" in the first-theme tutorial. | Ran it on `teme-dev` (under the shared lock). |
| 4 | doc | `first-theme.md` says to point `teme.theme_paths` at the theme folder; the dev-site page names the real setting, `TEME_THEME_PATHS` in `.env`. The first never mentions the env var, and neither says paths should be absolute on Windows or comma-separated for several themes (this site already had another entry). | One consistent name and the Windows form. | Used `TEME_THEME_PATHS` with an absolute `C:/…` path appended after the existing entry. |
| 5 | wall | **Fonts need a copy step.** The manifest's `fonts` key wants files in the theme's `public` folder with exact names, and the default theme's own stylesheet writes the `@font-face` rules by hand (the manifest only preloads). Nothing says whether core writes `@font-face` from the manifest. | `fonts` to be enough. | Wrote `@font-face` in `assets/css/fonts.css` and copy the Fontsource `woff2` files into `public/fonts` in the Vite build; listed them in `fonts` (first Latin file preloaded). |
| 6 | wall | **A skin cannot switch tokens or template sets from a theme setting out of the box.** Templates can: a dispatcher can read `$themeSettings['skin']` and include another folder. But `tokens` and `tokens_dark` are static in the manifest, and a `select` setting offers no way to say "this skin's tokens". | A setting such as `skin` selecting both the template set and the token set. | For the next update: ship each skin's tokens as CSS under a `[data-skin="…"]` wrapper (the layout puts `data-skin` on its wrapper), with the manifest carrying only the default skin's tokens; the site's accent then recolours only where a skin uses `--teme-accent`. Recorded as the WALL for that update. |
| 7 | wall | **Settings are limited to four types and four fieldsets** (`select`, `boolean`, `text`, `color`; `site`, `latest`, `content`, `archive`). A number (items per page, columns), a menu choice, an image (logo) or a repeater (social links, "our network" links) cannot be a setting. | Number and image settings. | Menus carry the lists (`social`, `footer`, `network` slots); numbers stay fixed. |
| 8 | wall | **Alpine needs its CSP build.** Teme's page policy gives a theme no `unsafe-eval`, so Alpine's normal build cannot run. The handbook says "Alpine.js only inside the theme's own scripts" nowhere; I found the need by reading how Alpine evaluates strings. The CSP build cannot evaluate `!x`, ternaries, object literals or assignments in attributes, so the drawings' attributes (`:class="{ on: active === s.id }"`, `x-text`) all had to move into JS getters. | A note in the handbook on scripts and the page policy. | Registered components in `assets/js/skins/fable.js` and kept attributes to property and method names. |
| 9 | wall | **`<x-teme::region>` cannot say which region it is in to the card it draws.** A theme's `cards/featured-posts.blade.php` receives only `$heading`, `$items`, `$images`, so one region's featured posts cannot be drawn differently from another's by the card view. | `$region` passed to the card view. | Wrapper classes around each `<x-teme::region>` in the template, and CSS on those wrappers. |
| 10 | wall | **No way to ask whether a region is empty.** A template can't test a region, so a band around it (newsletter, ads) cannot be left out in PHP. | `@regionHasContent('name')` or a component slot. | CSS `:has()`: the wrapper hides itself when the region drew nothing inside it. |
| 11 | doc | The kit (`teme/testing`) can make only a bare published item (`publish('Title')`): no category, author, image, tags, comments or body headings, so a theme's tests cannot cover those branches of a template. | `publish()` with fields, terms, authors, body. | Tested the empty and absent branches with the kit; filled content on the dev site through its own admin routes for screenshots (see REPORT.md). |
| 12 | doc | The test DB is one shared PostgreSQL for every project that runs `php artisan test`; several sessions running tests at once could collide. The testing page doesn't mention it. | A note on one test run at a time per checkout. | A lock directory around test runs among my own agents. |

## From the page work (home, article, listings) and the demo seed

| # | Kind | Finding | Expected | Did instead |
|---|---|---|---|---|
| 13 | wall | **No public way to put demo content into a site.** Categories, authors, menus and regions can be created only in the admin (needs a sign-in) or, for items and media, the management API (needs a key an administrator makes); the API cannot make terms or people at all. A theme's screenshots and audit need such content. | A documented seeding path (an artisan command or a public contract). | `seed/seed.php`, a dev-only script that calls Teme's own Operations the way the temecms theme's seed does: not part of the theme, flagged as a deviation from "outside developer only" in DECISIONS.md. It makes no categories or authors, so those branches are covered by the empty-state tests only. |
| 14 | doc | A **media field's stored value** is `{"id": "<media id>"}`. `theme.md` says a media `FieldView` has `value: string|null`; `fields.md` gives the field's key but not the shape a writer must send, and the refusal is only "Choose a file from the media library." | The shape, in `fields.md`. | Found by trying the likely shapes in turn (a bare id, lowercase, `teme:media/…`, then `{id}`). |
| 15 | wall | **`$page->bodyHtml` writes `h2` with no `id`**, although the Tiptap heading node carries one, so a theme cannot link to headings or build a contents list. The handbook does not say so. | An `id` on every heading, or a `headings` list on `ArticleView`. | `partials/article-body` parses `bodyHtml`, gives each `h2` an id made from its words (unique, an existing id kept) and builds the rail's "In this story" list from them. This rewrites core's HTML in the theme; a core option would remove it. |
| 16 | doc | **A word key can collide with Laravel's own language groups.** `__('Pagination')` returned Laravel's `pagination.php` array (on Windows's case-insensitive file system the key matched the group), so any listing with a second page threw a 500. The handbook says "English sentence as its key" and never warns about `auth`, `pagination`, `passwords` or `validation`. | A warning on the Words rule. | Used the key "Pages", as the default theme does; a test now renders page 2. |
| 17 | wall | **`teme:theme:check` budgets JavaScript at 5 KB compressed**, which Alpine's CSP build (about 24 KB) exceeds on its own, though the brief and the handbook's wording allow Alpine in a theme's own scripts. The command passes with a warning. | A budget that fits a framework, or guidance for it. | Kept Alpine; the warning stays. CSS is 11.1 KB of 15 KB. |
| 18 | doc | The markup core writes **around a region** (`div.teme-region.teme-region-NAME`) is not in `themes/regions.md`; the page agent found it only in `docs/architecture/themes.md`, a page outside an outside developer's reading list. Which also means the home agent's reading list broke the rule once: recorded here, nothing was copied from Teme's code. | The wrapper's class names in the regions guide. | Wrapped each region in a theme-owned element with its own class and styled that. |
| 19 | doc | **The public page's content security policy is not documented** for `data:` images and inline `style` attributes. The icon pattern uses a `data:` URI background and a `style` custom property. | A table of what a theme page may do. | Used both; only the admin policy was found. Verify on a real page before relying on it (REPORT.md). |
| 20 | wall | **The kit cannot set theme settings, fill a region, make a menu, term, author portrait or image**, so tests cover the empty branches only; the filled-region, kicker, portrait and snippet branches are checked by the demo seed and the browser audit instead. Also `ListingItem` has no reading time, tags or total count, `Person` has only name, url and bio, and nothing counts views, so "Quick reads", "Most read", counts and facets are dropped or become editor-chosen regions. | Fixtures in the kit; the data in the view models. | See FEATURES.md rows marked "can't yet". |
| 21 | wall | **A region cannot be shown by viewport.** The half-page ad (300 × 600) is drawn only from 1440 px, but its region is in the page at every width, so an ad's code in it still loads on a phone. | A breakpoint option on a region, or the region omitted by core. | Hidden with CSS only; an ad network's own responsive code is the editor's answer. |
| 22 | doc | **Whether `$page->url` is absolute is not stated**; share links need an absolute address. | One sentence in `theme.md`. | Made it absolute from `$site->url` when it is not. |
| 23 | wall | **A theme cannot place a section from a partial into the layout order cleanly**: the rail is drawn after the article's partial sets the contents list only because the layout renders the rail last. Teme has no slot or stack API for a theme's own chrome. | A documented way to pass data up to the shell. | Used Blade sections, which works. |
